# Required daemon across Homebrew install, upgrade and regeneration — Design

**Date:** 2026-09-27   **Status:** Approved   **Author:** Falconiere Barbosa (epic worker)   **Topic:** Falconiere/homebrew-tap#1: Homebrew channel lifecycle for comemory's required sync daemon

## Problem

The comemory engine now requires a resident sync daemon. Its managed installers
(`install.sh`, `comemory upgrade`, `scripts/dev-install.sh`) finish only once
`sync daemon ensure` proves a ready coordinator on the new binary (comemory#258).

`Formula/comemory.rb` has no lifecycle integration. A user who runs
`brew install` or `brew upgrade` is not told that the daemon is required. They
are also not told how to verify it, or that `brew uninstall` leaves a
launchd/systemd unit behind. The integration is also fragile: the formula is
regenerated by cargo-dist on every comemory release, so any hand edit here would
be erased by the next release.

Homebrew itself cannot start the service. Homebrew 7.0.6 runs `post_install`
inside a sandbox, with a fresh temporary `HOME` and no read access to the real
home. The legacy `post_install` is deprecated and audit-rejected, and a formula
has no uninstall hook. See the brainstorm
`docs/toolu/brainstorms/2026-09-27-brew-required-daemon.md`.

## Non-Goals

1. There is no formula `post_install`/`post_install_steps` that runs comemory,
   and no `service do` block or `brew services` unit (H-3: one naming scheme,
   owned by the engine).
2. No engine change. The unit's binary path (currently the canonical Cellar
   file) and preflight behavior belong to comemory. The stable `opt/` path is
   follow-up F-2.
3. No edit to comemory's `release.yml` or `scripts/replication/coverage.json`.
   This worker is authorized only for this repository. The call-site change is
   follow-up F-1 and the manifest rows are follow-up F-3.
4. No daemon opt-out, skip flag or "optional" wording.
5. No claim that the Homebrew channel fully supports immediate required-daemon
   start (H-6).

## Architecture

There are three parts, all in this tap:

1. **Formula lifecycle contract.** `Formula/comemory.rb` gains a `caveats`
   method that states:
   - the daemon is required and Homebrew cannot start it;
   - run `#{opt_bin}/comemory sync daemon ensure` after install, upgrade or
     reinstall (the stable opt path, H-1);
   - `comemory upgrade` updates through Homebrew and verifies the daemon;
   - run `comemory sync daemon uninstall` before `brew uninstall`;
   - the data directory is never removed.

   Homebrew prints caveats at the end of every install, upgrade and reinstall.
   That printed text is the explicit report of the lifecycle limitation (H-2).
   Caveats are plain text, so evaluating the formula, building a bottle and
   generating completions start nothing.
2. **Regeneration guard: `scripts/comemory_formula.rb`.** The tap owns the
   patch, so the publishing step only has to call it.
   - `apply FILE` idempotently inserts the completions call (the same
     four-shell block `release.yml` injects today) and the `caveats` method into
     a cargo-dist-generated formula. It tolerates a file that already has
     completions.
   - `check FILE` exits non-zero and lists each missing or forbidden element.
   - It runs in tap CI on every push to any branch (so on every PR head) and to
     `main`, including the release bot's pushes, which a GitHub App token does trigger. A regeneration
     that drops the contract therefore turns the release commit red instead of
     passing silently (H-4).
   - It also runs against the **real** raw formula asset from the latest
     comemory release, in the form the next release will publish.
3. **Real-brew lifecycle test: `scripts/test-brew-lifecycle.sh`.** It is driven
   by `.github/workflows/lifecycle.yml` on disposable runners:
   - `macos-15`, native launchd (Homebrew 7 marks macOS 14 unsupported);
   - `ubuntu-22.04`, native `systemd --user` with linger;
   - `ubuntu-22.04`, headless, expecting the `process` supervisor.

   It taps this checkout, runs a current `brew update`, then installs,
   reinstalls, upgrades and uninstalls the real formula (real release
   artifacts). It reads readiness only from the engine's own
   `sync daemon ensure --json` / `sync daemon status --json` and inspects real
   unit files, processes and SQLite rows. Its native-mode preconditions follow
   the engine's `test-daemon-install.sh` (D10): it refuses to run unless
   `CI=true` or `COMEMORY_DISPOSABLE_ENV=1`.

The decisive trade-off is that honest, verified readiness through named CLI
commands wins over an in-formula hook. That hook would run against a throwaway
`HOME` and claim readiness that is not real. It is kept only as a CI probe that
proves the limitation.

## Interfaces / Schema

- `ruby scripts/comemory_formula.rb apply <formula.rb>` rewrites the file in
  place and exits 0. It exits 1 when the anchors `    install_binary_aliases!\n`
  (exactly once) or the final `end` of the class are missing.
- `ruby scripts/comemory_formula.rb check <formula.rb>` exits 0 or 1. On failure
  it prints one line per problem to stderr, prefixed `contract:`. The contract
  requires:
  - `generate_completions_from_executable(` with `shells: [:bash, :zsh, :fish, :pwsh]`;
  - `def caveats` containing `sync daemon ensure`, `#{opt_bin}/comemory`,
    `comemory upgrade` and `sync daemon uninstall`.

  It forbids:
  - `post_install`;
  - `service do`;
  - any other `sync daemon` invocation outside `caveats`;
  - opt-out wording inside `caveats` (case-insensitive `optional`, `skip`,
    `opt out`, `opt-out`, `--no-daemon`, `disable`), for H-5.

  **Matching rule:** line-based and literal, over non-comment lines (a leading
  `#` after indentation marks a comment). The `caveats` region runs from
  `def caveats` to the first line at the same indentation that is exactly
  `end`.
- `bash scripts/test-formula-contract.sh [--release-formula PATH] [--fixtures-only]`
  is the contract test. It fetches the latest release's `comemory.rb` with `gh`
  when no path is given.
  - Fixture cases: the raw release asset, the v0.51.0 publisher output
    (`git show 51f149b:Formula/comemory.rb`), and boundary copies of both.
  - Repository cases: committed `Formula/comemory.rb` passes `check`, and the
    README carries the AC-7 statements. `--fixtures-only` skips these.
- `bash scripts/test-brew-lifecycle.sh --native|--headless|--self-test` is the
  lifecycle test. `--self-test` is a syntax and consistency check only: it
  verifies that the script refuses to run outside a disposable environment
  (exit 2). It proves no AC. Env: `CI` / `COMEMORY_DISPOSABLE_ENV`, `TAP_DIR` (defaults to the repo
  root). Exit 0 means every scenario passed. Each scenario prints
  `PASS <name>` or `FAIL <name>: <reason>`.
- `bash scripts/check-ci-run.sh <workflow-file> <sha> <expected-jobs>` is
  delivery evidence. It selects the newest `push` run of the workflow at that
  SHA and polls every 30 s (`gh run view --json`) until it completes, for at
  most 90 min by default (override with `CI_RUN_TIMEOUT_SECS`). It then requires
  exactly `<expected-jobs>` jobs, each concluding `success`, and prints each
  job's name and conclusion.
  - Exit 0: all jobs succeeded.
  - Exit 1: the run failed, the job count is wrong, a job concluded otherwise,
    or no run exists after a 5 min grace period.
  - Exit 2: bad arguments or a `gh` error persisting across 3 consecutive polls.
- `.github/workflows/lifecycle.yml` has jobs `contract` (ubuntu) and
  `brew-lifecycle` (the matrix above). Triggers: `push` to any
  branch, which covers the PR head and `main`, including release-bot pushes,
  plus `workflow_dispatch`. `pull_request` is omitted so no run is
  duplicated.

## Failure modes and edge cases

- **Generated formula lacks anchors** (cargo-dist changes shape):
  `apply` exits 1 naming the anchor, and the publishing step aborts before its
  commit (after F-1). Tap CI `check` fails on any formula committed without the
  contract.
- **Formula already has completions** (today's `release.yml`): `apply` adds only
  the caveats, and a second `apply` is byte-identical.
- **Hook probe:** a test-only formula whose legacy `post_install` runs `ensure`.
  After its install, the real `$HOME/.comemory` must have no ready coordinator
  and no unit. The probe's recorded output must show failure or a data dir
  outside `$HOME/.comemory`. This is observed evidence for H-2. The test asserts
  it, and it never counts toward readiness.
- **brew install alone:** asserts that brew started nothing (`status` reports
  `not_running`, no unit, no coordinator) and printed the caveats. Readiness is
  claimed only after `ensure --json` reports ready with the expected version,
  canonical binary and data dir.
- **No user service manager (headless Linux):** `ensure` falls back to the
  `process` supervisor. The test expects `process` there and the native kind
  elsewhere, so a silent fallback fails the native jobs. `ensure` failure
  (`ready:false`, exit 69) propagates as a test failure with the JSON printed.
- **Reinstall of the same version:** the same Cellar path gets a new inode. After
  `ensure`, the pid and `binary_file` change and the old pid is gone.
- **Upgrade with Cellar path change:** the formula gains `revision 1` in the
  tapped copy, so the keg becomes `<ver>_1`. After an ordinary command and then
  `comemory upgrade --json`, the daemon's binary equals `realpath(opt)`, no
  process runs the old keg path, and there is exactly one coordinator.
- **Queued operations:** pending `replica_operation` rows, `memories` rows and
  memory files are byte-identical before and after reinstall and upgrade. The
  empty-queue case is intentionally not asserted separately, because it is a
  subset of the non-empty one.
- **Uninstall:** `sync daemon uninstall` then `brew uninstall` leaves no unit and
  no coordinator, and the data is untouched.
- **brew uninstall without the CLI step:** the unit is left behind. The test
  asserts the leftover (the documented limitation), then removes it with
  `launchctl bootout`/`systemctl --user disable --now`.
- **Concurrency:** this spec assumes, without testing, that brew's own lock
  serializes installs of one formula. Concurrent installers are covered by the
  engine's `install.sh` race scenario, not by this channel.

## Acceptance criteria

- **AC-1:** (H-1, partially — manual step; H-2) Given the real formula, `brew install` prints caveats
  naming `<prefix>/opt/comemory/bin/comemory sync daemon ensure` and starts no
  service. Then that exact command returns `ready:true` with
  `daemon.version` equal to the formula version, `daemon.binary` equal to
  `realpath(opt/comemory/bin/comemory)`, `daemon.data_dir` equal to
  `$HOME/.comemory` and the expected supervisor. One coordinator and one unit
  exist, and the user never authenticated. H-1's automatic invocation "after
  binary installation" is impossible inside Homebrew (see Problem). The formula
  names the command, and the PR must not claim that H-1 is met automatically.
- **AC-2:** (H-2) A formula whose legacy `post_install` runs `ensure` does not
  produce a ready daemon for the real `$HOME/.comemory`, and leaves no unit
  there.
- **AC-3:** (H-3) With pending operations queued, `brew reinstall` followed by
  `ensure` restarts on the new file: pid and `binary_file` change, the old pid
  is gone, there is one coordinator, and the snapshot is identical.
- **AC-4:** (H-3) With pending operations queued, a `brew upgrade` that changes
  the Cellar keg, followed by `comemory upgrade --json`, reports
  `daemon.ready:true`. The binary is the new keg file, no process runs the old
  keg path, there is one coordinator and one unit, and the snapshot is
  identical.
- **AC-5:** (H-4) `check` fails on the real raw release `comemory.rb` and names
  the missing caveats and completions. `apply` then `check` passes, and a second
  `apply` is idempotent. `check` passes on committed `Formula/comemory.rb`, and
  CI runs it on every push to any branch, which covers PR heads and `main`. H-4 is detected in tap CI
  only after the push. The pre-publish gate lands only with F-1, and the PR
  states this.
- **AC-6:** (H-5) `comemory sync daemon uninstall` then `brew uninstall
  comemory` leaves zero comemory units and zero coordinators, with the data
  snapshot and memory files intact. `brew uninstall` alone leaves the unit
  behind; this is detected and documented, not hidden.
- **AC-7:** (H-6) README states:
  - the supported post-install readiness commands;
  - that the Homebrew channel does not fully support immediate required-daemon
    start (a release blocker for claiming it);
  - the uninstall order;
  - links to the engine install/upgrade contract.

## Hook probe evidence (CI run 36365607407)

On macos-15, ubuntu-22.04 native and headless, a legacy `post_install` that
runs `comemory sync daemon ensure --json` completes, and `brew install` exits 0,
with `ensure` reporting success. However, it ran with
`HOME=/private/tmp/.../comemory-hook-probe-postinstall-*` (or `/var/tmp/...`),
so the daemon it verified serves a throwaway data directory. The user's
`~/.comemory` had no daemon and no unit. A formula hook would therefore claim
readiness falsely, which H-2 forbids.

## Open Questions

- Q-1 (resolved by CI runs 36365419520 and 36365607407): after `brew upgrade` to a new keg,
  engine preflight alone moves the daemon only when brew has cleaned up the old
  keg.
  - On macOS 14 and 15 the old keg was kept, and after an ordinary command the daemon
    still ran `Cellar/comemory/0.51.0/bin/comemory`.
  - On Linux the old keg was removed, and preflight moved the daemon to
    `0.51.0_1`.
  - In both cases `comemory upgrade` settled the daemon on the new keg (AC-4).
    This is evidence for F-2: a same-version coordinator on an old, surviving
    keg is accepted.
- Q-2 (resolved; the orchestrator authorized comemory PRs, and this tap PR
  merges after them):
  - F-1 and F-3 are
    [Falconiere/comemory#311](https://github.com/Falconiere/comemory/pull/311).
    - `release.yml` applies and then checks `scripts/comemory_formula.rb`
      before committing the formula.
    - The real step runs in CI against a tap clone.
    - It adds the `homebrew` / `release-formula` replication cases and rows
      H-1…H-6.
  - F-2 is
    [Falconiere/comemory#312](https://github.com/Falconiere/comemory/pull/312),
    merged.
    - Preflight replaces a coordinator on a keg that `opt` no longer names.
    - Units run the `opt` link.
    - A real-brew keg-upgrade test covers macOS, Linux and headless.
- F-4 is [Falconiere/comemory#314](https://github.com/Falconiere/comemory/pull/314),
  which the orchestrator requires before this PR merges. It fixes an
  intermittent macOS race in the engine's `supervisor::bootstrap_or_replace`.
  - What happens: after `brew reinstall`, the evicted coordinator's label is
    still loaded. `launchctl bootout` returns before launchd finishes, so the
    immediate re-`bootstrap` fails with `5: Input/output error`. The process
    fallback then loses `daemon.lock` to the dying coordinator, and `ensure`
    exits 69.
  - Frequency: seen once in three macos-15 runs (tap run 36368419887, attempt
    1; the rerun was green).
  - The fix waits, with a bound, until `launchctl print gui/<uid>/<label>`
    fails before re-bootstrapping. A real-launchd test repeats the eviction
    and re-bootstrap path 25 times.
  - This tap's `reinstall` scenario stays strict. Until a release carries the
    fix, the released engine the formula installs can still hit the race.
